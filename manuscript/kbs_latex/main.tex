\section{Introduction}

Sequential recommendation derives user preferences from ordered interactions, yet stronger sequence encoders do not settle whether a distinct source of relationship history improves an already trained recommender. SASRec and BERT4Rec exemplify advances in next-item sequence modeling \cite{kang2018sasrec,sun2019bert4rec}; a separate knowledge-based decision is whether an available relationship specialist supplies \emph{additional ranking utility} for the current user, Base model and candidate set. This question concerns the benefit of using evidence, rather than its quantity alone.

Approaches to adaptive recommendation fuse collaborative, semantic, structural and temporal signals \cite{xie2026mhgfcl,zhu2026mifusr}. Such integration improves representations, but it need not tell us when a particular already available evidence specialist is preferable to the current Base. We call the difference between their ranking utilities on the same request \emph{Base-relative evidence value}. By treating the specialist as a selectable alternative, this operational quantity connects evidence assessment with expert-choice decisions \cite{narasimhan2022posthoc,mao2025mastering}.

Live-streaming recommendation makes this problem observable: user--creator relationships can persist across sessions while available ranking candidates vary with time \cite{rappaz2021liverec}. KuaiLive distinguishes room sessions from streamer identity; Twitch/LiveRec provides availability-aware streamer ranking \cite{qu2026kuailive,rappaz2021liverec}. We compare a transparent relationship-memory specialist with sequential Bases and distinguish relationships represented in the Base input, recoverable from earlier history, and absent from recorded eligible history. These target-relative states characterize the observed gains, while a separate predictor uses only pre-outcome information to decide when to invoke Memory.

Two complementary tests examine the same value criterion. A frozen Twitch/LiveRec decision experiment first establishes that Memory's aggregate disadvantage conceals favorable conditional cases and that pre-outcome utility prediction can improve selective ranking. A paired KuaiLive analysis then shows that the sign of Memory's advantage over Base can change with the ranked candidate environment despite fixed events and model parameters. Taken together, these results separate \emph{whether evidence can help}, \emph{when it should be selected}, and \emph{which evaluation context defines its observed value}.

The contributions are:
\begin{itemize}
    \item \textbf{Operational valuation of relationship evidence (C1).} We define event-level incremental ranking utility for a fixed relationship specialist relative to a designated Base, and characterize its dependence on target-history conditions.
    \item \textbf{Candidate-regime dependence (C2).} We compare matched candidate protocols at fixed checkpoints, decompose their observed ranking-reference contrast, and examine its stability across trained checkpoints and negative candidate draws.
    \item \textbf{Relative-utility-guided decisions (C3).} We learn a pre-outcome estimate of specialist benefit and assess a DEV-frozen policy against Base, equal-count Base Difficulty and a retrospective hindsight bound.
\end{itemize}
The formulation is general to fixed alternative rankers; empirical evidence concerns the reported live-streaming settings and offline candidate protocols.

\section{Related Work}

\subsection{Sequential and Long-Horizon Recommendation}

Sequential recommenders use ordered interactions to represent changing preferences, with SASRec and BERT4Rec providing widely used self-attentive foundations \cite{kang2018sasrec,sun2019bert4rec}. Later augmentation, contrastive, multi-interest and multi-granular methods extend the temporal information accessible to a Base \cite{ni2025idmarec,sheng2025dsmgrec}. Such work concerns how a predictor \emph{represents} history. Our complementary question concerns how much an additional, fixed relationship-evidence ranker \emph{improves the decision} after that representation has already been trained.

\subsection{Auxiliary Evidence Integration and Reliability}

Auxiliary evidence is often introduced by adaptive fusion. Multi-head gating integrates collaborative, semantic and structural views across preference horizons \cite{xie2026mhgfcl}; mutual-information-guided fusion addresses multimodal complementarity and redundancy \cite{zhu2026mifusr}; denoising and modality balancing further manage heterogeneous inputs \cite{zhang2026mcd4sr}. KAPER instead selects temporally and structurally relevant knowledge paths for re-ranking \cite{kim2026kaper}. These advances improve signal construction and combination. Whether a separately specified evidence ranker improves an incumbent Base for a given request remains a different decision-level question.

Reliability-aware integration can downweight uncertain content or interactions \cite{huo2026reliability}, while negative-transfer studies document that extra pretrained information may impair sequential ranking \cite{peng2025negative}. Conditional gating between structured and textual knowledge provides a related perspective outside recommendation \cite{yerragunta2026gating}. Crucially, even reliable evidence can be \emph{redundant}: the Base may already provide the same useful ranking signal. This motivates estimating incremental utility, not merely source quality.

Decision-theoretic value of information measures changes in expected action utility when information becomes available \cite{abbas2025voi}. Here the information source has already been instantiated as a ranking specialist, and the actionable choice is whether to use its ranking instead of an existing Base. The relevant value is therefore model- and request-relative.

\subsection{Expert Routing and Learning-to-Defer}

Learning-to-Defer (L2D) studies allocating predictions between a model and external experts, including cost-sensitive formulations \cite{mozannar2020defer}, post-hoc rules for existing predictors \cite{narasimhan2022posthoc}, and newer approaches to consistency and changing expert pools \cite{mao2025mastering,montreuil2026online}. Adaptive recommendation experts, including CeDRec, provide a related representational route \cite{sun2025cedrec}. These approaches motivate a selection rule but do not by themselves establish the event-wise value of a particular relationship-history ranking expert.

Our evaluation therefore connects expert choice to a measurable ranking target: the difference between specialist and Base utility on the same candidates. Predicting this difference and predicting the Base's own difficulty are distinct learning objectives; comparing their selected events at the same invocation count tests that distinction.

\subsection{Live-Streaming and Repeat-Aware Recommendation}

Live-streaming recommendation couples persistent creator relationships with transient room or stream availability. Viewer--anchor, dynamic-room, interaction-aware and graph approaches describe complementary aspects of this setting \cite{zhang2021bidirectional,gao2023driver,chen2024preference,yu2024hypergraph,zhu2025repeated}. LiveRec models availability and repeat consumption directly \cite{rappaz2021liverec}, while KuaiLive connects ephemeral rooms with stable streamer identities \cite{qu2026kuailive}. This combination makes both the Base's accessible history and the population against which specialist utility is measured consequential.

\subsection*{Research Gap}

Prior work explains how to represent long histories, fuse auxiliary signals and route among experts; sampled-ranking studies further warn that measured model orderings depend on evaluation candidates \cite{krichene2020sampled}. The open empirical connection is to \emph{value a fixed relationship-evidence ranker relative to an incumbent Base at the event level}, identify the historical and candidate conditions in which that value arises, and test whether pre-outcome features support useful choices. Section~\ref{sec:problem} formalizes this decision quantity.

\section{Problem Formulation}
\label{sec:problem}

The formulation follows the decision from an eligible ranking event to its realized specialist benefit, its pre-outcome conditional expectation, and the resulting choice of ranking. The same event-level definition supports both a selective policy and comparisons across candidate environments.

\subsection{Recommendation Setting and Event-Level Ranking Utility}
\label{sec:event-utility}

For user $u$ at recommendation time $t$, let the pre-outcome decision context under evaluation regime $r$ be $\xi_r=(u,t,\mathcal{C}^{(r)}_{u,t},\mathcal{H}_{u,t})$, where $\mathcal{C}^{(r)}_{u,t}$ is the candidate set under that regime and $\mathcal{H}_{u,t}$ is the interaction history available strictly before $t$. An evaluated event is $x_r=(\xi_r,y)$, where $y\in\mathcal{C}^{(r)}_{u,t}$ is the observed relevant target. The underlying interaction instance $(u,t,y,\mathcal{H}_{u,t})$ may be held fixed while different candidate-set constructions produce distinct decision contexts and, hence, distinct full events. Ranking models receive the context but not $y$, which is used only for offline evaluation. For concision, the subscript $r$ on $\xi$ and $x$ is omitted when a regime is fixed.

Let $A$ be a ranking model and let $r_A(y\mid\xi)$ denote the 1-indexed rank assigned to $y$ among $\mathcal{C}_{u,t}$. For cutoff $K$, define the event-level ranking utility
\begin{equation}
    u_K(A,x)=
    \begin{cases}
        \displaystyle \frac{1}{\log_2\!\left(r_A(y\mid\xi)+1\right)}, & r_A(y\mid\xi)\le K,\\[6pt]
        0, & r_A(y\mid\xi)>K.
    \end{cases}
    \label{eq:event-ndcg}
\end{equation}
With one relevant target per event, Eq.~\eqref{eq:event-ndcg} is its NDCG@$K$ contribution; the mean across events is aggregate NDCG@$K$. Candidate construction enters the metric through the ranked alternatives, allowing the same user--target interaction to have different ranking utilities under different regimes.

\subsection{Base-Relative Specialist Utility}
\label{sec:relative-utility}

Let $B$ denote a fixed base recommender and $M$ a fixed relationship-memory specialist. For a given selective-decision experiment, both rank the same event-specific candidate set and are fixed before the invocation policy is learned. We define the specialist-minus-base utility
\begin{equation}
    \Delta_M(x)=u_K(M,x)-u_K(B,x).
    \label{eq:delta-memory}
\end{equation}
The sign of $\Delta_M(x)$ states whether the specialist improves, ties or worsens Base's ranking for the evaluated request. This is an \emph{operational} measure relative to a specified model pair and candidate regime: history acquires value through the improvement in the decision it enables.

The realized $\Delta_M(x)$ is an offline supervisory quantity because computing it requires the observed target $y$ and the rankings produced by both $B$ and $M$. Selective specialist use must therefore estimate its conditional expectation from information available before $y$ is known.

\subsection{Conditional Relative Utility}
\label{sec:conditional-utility}

Let $R$ index the operating recommendation condition under which candidate construction, temporal availability, or related protocol elements are fixed, and let $Z$ denote the information available at invocation time. We condition on $R=r$ to describe a regime-specific event distribution; $R$ need not be an explicit feature of $Z$. The variable $Z$ is constructed only from pre-outcome information, such as user and history summaries, candidate-set descriptors, and confidence signals produced by the base recommender. Define the conditional specialist-minus-base utility as
\begin{equation}
    \eta_r(z)
    =\mathbb{E}\!\left[\Delta_M(X)\mid Z=z,R=r\right].
    \label{eq:eta}
\end{equation}
When training and evaluating within a fixed regime, we suppress $r$ for notational simplicity. A learned estimator $\hat{\eta}_r(z)$ scores events by expected specialist-minus-base value; Section~4 specifies its implementation.

Let $a(Z)\in\{0,1\}$ denote a pre-outcome selection policy, where $a(Z)=0$ uses the base ranking and $a(Z)=1$ uses the specialist ranking. This includes development-frozen score-threshold policies but excludes any dependence on the realized target. For an evaluated event $x$, define $u_K^{\mathrm{sel}}(x;a)=(1-a)u_K(B,x)+a\,u_K(M,x)$. The expected improvement over always using the base satisfies
\begin{align}
    &\mathbb{E}\!\left[u_K^{\mathrm{sel}}(X;a)-u_K(B,X)\mid R=r\right] \\
    &\qquad=\mathbb{E}\!\left[a(Z)\Delta_M(X)\mid R=r\right]
    =\mathbb{E}\!\left[a(Z)\eta_r(Z)\mid R=r\right].
    \label{eq:expected-selective-gain}
\end{align}
Equation~\eqref{eq:expected-selective-gain} gives the decision rationale for estimating $\eta_r$: under a fixed regime, expected gain over the base is determined by which events are selected and their conditional relative utility.

The selector sees only $Z$, never the target $y$ or the realized utility difference. Later evidence-state groups and target-specific recurrence distances are retrospective outcomes, separate from decision-time inputs. Base Difficulty estimates the quality of $B$ alone; the desired $\eta_r$ estimates the \emph{difference} between the two rankings. A difficult Base event can therefore still be unsuitable for Memory.

\subsection{Selective Invocation and Equal-Count Comparison}
\label{sec:decision-rule}

Given $\hat{\eta}_r(z)$, a threshold selects the specialist whenever its predicted incremental value exceeds the development-selected operating threshold $\tau_r$:
\begin{equation}
    a_{\tau_r}(z)=\mathbf{1}\!\left[\hat{\eta}_r(z)>\tau_r\right],
    \label{eq:utility-threshold}
\end{equation}
where a selected event uses $M$ and an unselected event uses $B$. This rule does not enforce an exact invocation count across future requests. The training and threshold-selection protocol is given in Section~\ref{sec:exp-freeze}.

At evaluation, the number of specialist calls produced by the fixed rule defines $m=\sum_{i=1}^{n}a_{\tau_r}(z_i)$. Matching another method to this same count isolates \emph{which events} it selects from \emph{how many} times the specialist runs. The score objectives and retrospective matching procedure are specified in Section~\ref{sec:exp-comparators}.

\subsection{Regime-Level Utility Decomposition}
\label{sec:regime-decomposition}

A change in aggregate specialist value can reflect a changed distribution of evidence states, changed state-conditional ranking value, or both. Let $S$ be an exhaustive partition of target-relative relationship states, operationalized in Section~\ref{sec:framework-states}. With $\bar{\Delta}_r=\mathbb{E}[\Delta_M(X)\mid R=r]$, total expectation gives
\begin{equation}
    \bar{\Delta}_r
    =\sum_s P(S=s\mid R=r)
    \,\mathbb{E}\!\left[\Delta_M(X)\mid S=s,R=r\right].
    \label{eq:regime-decomposition}
\end{equation}
Equation~\eqref{eq:regime-decomposition} is a descriptive partition of value across states. It provides a common account of history-related heterogeneity even when the underlying candidates or Base change; the methods in Section~\ref{sec:experimental-setup} specify which quantities are held fixed in each experiment.

\subsection{Strong Sequential Base Recommenders}
\label{sec:framework-base}

KuaiLive uses a Dual-ID sequential Base with room-level and streamer-level SASRec branches. The room branch represents individual live sessions; the streamer branch connects sessions involving one creator. Both score the eligible \emph{rooms}, and their within-candidate standardized scores are fused by development-selected coefficients. This preserves the room prediction task while providing persistent identity context. Fusion settings for the distinct evaluated protocols belong to Section~\ref{sec:exp-freeze}.

For Twitch/LiveRec, Base is the availability-aware LiveRec recommender \cite{rappaz2021liverec}, including context and repeat-consumption components (input length 16). Both datasets therefore instantiate the same Base-relative decision criterion with different recommendation units and incumbent model architectures; Section~\ref{sec:exp-data} specifies their candidates and time splits.

\subsection{Transparent Relationship-Memory Specialist}
\label{sec:framework-memory}

The specialist $M$ scores eligible candidates from historical user--creator interactions available before the target time. Let $i$ denote a candidate creator, let $n_{u,i}(t)$ be its count in the eligible pre-target history, and let $n_{u,\max}(t)$ be the largest such creator-specific count for user $u$. Define a long-term relationship strength as $\mathrm{Long}(u,i,t)=n_{u,i}(t)/\max\{1,n_{u,\max}(t)\}$. For the ordered last $K_s=10$ eligible user--creator interactions, let $d$ be the reverse interaction index ($d=0$ for the most recent). The short-term component is $\mathrm{Short}(u,i,t)=\max_{\{d:i_d=i\}}\exp(-d/3)$, with a maximum over an empty set defined as zero. Hence repeated appearances contribute their most recent decayed strength rather than an unbounded sum.

The popularity component $\mathrm{Pop}(i)$ is derived from eligible training-split creator counts by applying $\log(1+n_i)$ and min--max scaling over observed creators; unseen creators receive zero. The fixed specialist score is
\begin{equation}
s_M(u,i,t)=
0.45\,\mathrm{Short}(u,i,t)
+0.45\,\mathrm{Long}(u,i,t)
+0.10\,\mathrm{Pop}(i).
\label{eq:memory-scoring}
\end{equation}

The same scoring coefficients, short-history horizon and decay are used on both platforms; a candidate without prior interaction may still receive a nonzero popularity score. Candidates are ordered by score with deterministic identifier-based tie-breaking. In KuaiLive, distinct rooms mapped to one creator can consequently share a Memory score; Twitch candidates are streamers directly. The eligibility of pre-target records and platform-specific timing conventions are given in Section~\ref{sec:exp-data}. The fixed specialist supplies an interpretable alternative ranking rather than a learned fusion layer.

\subsection{Base-Relative Relationship-Evidence States}
\label{sec:framework-states}

We operationalize the diagnostic variable $S$ introduced in Section~\ref{sec:regime-decomposition} using the target creator and pre-target history. Let $V_L(x)$ indicate that the target creator occurs in the sequence visible to a base with input length $L$, and let $H(x)$ indicate that the same creator occurs anywhere in the eligible pre-target relationship history. Then
\begin{equation}
S_L(x)=
\begin{cases}
\text{represented},&V_L(x)=1,\\
\text{recoverable but unrepresented},&V_L(x)=0,\ H(x)=1,\\
\text{unavailable},&V_L(x)=0,\ H(x)=0.
\end{cases}
\label{eq:diagnostic-states}
\end{equation}

These states are properties of the \emph{observed target relative to the Base input}, not of a directly observable deployment label. Represented means visible in the input window; it does not assert successful representation learning. None of $S_L$, target recurrence distance or realized $\Delta_M$ is included in the decision-time vector $Z$.

\subsection{Observable Features and Conditional Relative-Utility Estimation}
\label{sec:framework-estimation}

The estimator $\hat{\eta}_r(z)$ predicts the development-event utility difference $\Delta_M(x)$ from pre-outcome history and Base-score descriptors. Six history features summarize log history length, creator repeat rate, normalized preference entropy, old-versus-recent Jensen--Shannon drift, circular temporal regularity, and composite history complexity. On Twitch, regularity uses phases modulo $144$ ten-minute steps, representing a daily cycle. Eight Base-score features comprise score standard deviation and range, top-1/top-2, top-1/top-5 and top-10/top-11 margins, the top score's standardized value, normalized score entropy, and top-ten softmax mass. These quantities summarize candidate ranking patterns; entropy and softmax mass are not assumed to be calibrated uncertainty estimates.

The composite history-complexity descriptor weights percentiles of entropy, preference drift and log history length by $0.4$, $0.4$ and $0.2$. For Twitch, the reference percentile distributions are determined from unlabeled development features and then reused during evaluation; KuaiLive uses eligible split-specific past-history reference pools. These transformations are based on pre-outcome information, not the target or the diagnostic evidence state. Training the regression estimator, selecting its threshold and evaluating frozen policies are described in Section~\ref{sec:exp-freeze}.

\subsection{Specialist Selection and Matched-Budget Controls}
\label{sec:framework-controls}

At decision time the system scores candidates with Base, constructs $Z$, estimates $\hat{\eta}_r(Z)$ and invokes Memory only if the threshold rule in Eq.~\eqref{eq:utility-threshold} selects it. The method consequently uses history evidence as a conditional alternative ranking rather than fusing its score indiscriminately into every Base result.

For evaluation we compare the Utility score with a Base-Difficulty objective that predicts $1-u_K(B,x)$ from the same feature family. The independent roles of these predictors follow Eq.~\eqref{eq:eta}; the retrospective equal-count comparator and hindsight Oracle are defined in Section~\ref{sec:exp-comparators}, where their label access and evaluation limits can be specified precisely.


\section{Experimental Setup}
\label{sec:experimental-setup}

Two evidence settings test the same Base-relative question. Twitch/LiveRec supplies the frozen ranking-choice test and history-conditional diagnostics. KuaiLive supplies matched, fixed-checkpoint candidate-regime comparisons that probe when the measured advantage changes with the alternatives ranked. The model, evaluation population and candidates within each setting are summarized in Table~\ref{tab:exp-datasets}.

\subsection{Datasets and Prediction Tasks}
\label{sec:exp-data}

\paragraph{KuaiLive.}
KuaiLive provides live-shopping interactions associated with time-bounded live-room sessions and streamer identities \cite{qu2026kuailive}. The task is next-\emph{room} recommendation; relationship-memory features are defined at the \emph{streamer} level and assigned to candidate rooms through the room--streamer mapping. The primary evaluation uses a chronological leave-last-two-out split per eligible user: earlier interactions form the training history, the penultimate event supplies the development target, and the final event supplies the test target. After eligibility filtering and interaction deduplication, development and test each contain one target for each of 10,222 users. At test time the earlier development interaction is eligible history, while global streamer popularity is estimated from training interactions.

Room availability is determined from recorded session start and end times, using the half-open interval $[t_{\mathrm{start}},t_{\mathrm{end}})$. In the \emph{sampled-active} protocol, the positive target is ranked with 574 distinct, contemporaneously active non-target rooms sampled without replacement. In the \emph{full-active} protocol, the same user--time--target event is ranked against the active-room set, retaining the observed target where its recorded session interval is inconsistent with that set. The two protocols share evaluated events but differ in candidate-set size and score-normalization population. The non-target rooms are evaluation negatives rather than verified dislikes and may include rooms visited previously. Hence sampled metrics are evaluated as a distinct candidate protocol rather than substitutes for full-active metrics \cite{krichene2020sampled}.

\paragraph{Twitch/LiveRec.}
The second task recommends \emph{streamers} using the chronological, availability-aware Twitch/LiveRec protocol \cite{rappaz2021liverec}. User--streamer activity is recorded in ten-minute crawl steps; start and stop denote first and last observations rather than exact session boundaries. Candidate streamers are restricted to those available at the prediction step. The primary LiveRec base uses a maximum context of 16 interactions. The frozen development and test sets contain 46,878 and 44,221 one-positive target events, respectively. Memory history in the primary analysis admits records first observed before the target step, whereas the training-only popularity prior uses records ending before the training cutoff. A stricter split-end history definition is evaluated separately as a sensitivity analysis. Neither protocol assumes observation timing finer than the crawl resolution.

\subsection{Baselines and Compared Methods}
\label{sec:exp-comparators}

For KuaiLive, the principal base is the Dual-ID sequential recommender described in Section~\ref{sec:framework-base}. Room- and streamer-identity SASRec branches produce scores that are standardized separately within the eligible candidate set and combined using a development-selected fusion weight. Auxiliary popularity, individual SASRec, GRU4Rec, and ContraRec--BERT4Rec benchmarks assess the reference's competitiveness under documented candidate protocols with heterogeneous training/tuning budgets (Supplementary~S3). The paired specialist-value estimand retains its designated, separately frozen Base. For Twitch, the principal base is the official LiveRec model with contextual and repeat-consumption components enabled. The two platforms use different base architectures; the object of comparison is the specialist's utility \emph{relative to each platform's designated base}.

The specialist is the fixed Short--Long--Popularity scorer in Eq.~\eqref{eq:memory-scoring}. Against each platform's designated Base we compare always-Base, always-Memory and DEV-trained Utility selection. Base Difficulty uses the same 14 pre-outcome descriptors to estimate $1-u_{10}(B,x)$; a hindsight Oracle ranks by realized $\Delta_M$. For an equal-call assessment both comparators select the $m$ events chosen by the frozen Utility policy across the TEST batch. Difficulty's top-$m$ operation is retrospective; only the Utility threshold is evaluated as a separately frozen pointwise choice. These controls concern selection quality rather than zero-shot gate transfer between platforms.

\subsection{Experimental Protocols}
\label{sec:exp-freeze}
\label{sec:exp-regimes}

\paragraph{Training and model selection.}
Base models are trained on the designated training split; architecture-specific hyperparameters and fusion coefficients are selected using development data. The relative-Utility and Base-Difficulty estimators use the same 14 observable descriptors specified in Section~\ref{sec:framework-estimation} and histogram-gradient-boosted regression. Five-fold out-of-fold (OOF) development predictions support Utility threshold selection by mean development ranking utility, with ties favoring fewer specialist invocations. The one-target-per-user protocols use shuffled KFold; the separate global-time KuaiLive analysis, which can contain multiple events per user, uses user-grouped folds. Final estimators are fitted on development data and evaluated with fixed transformations and thresholds on the held-out test set. On Twitch, feature percentiles use an unlabeled development reference retained for test transformation; KuaiLive constructs its history percentiles from the eligible past-history pool of the corresponding split. Detailed transforms and hyperparameters are provided in the supplementary implementation protocol.

\paragraph{Candidate-regime comparisons.}
KuaiLive is evaluated under sampled-active and full-active candidate sets. Native regime comparisons use their respective development-selected base configurations; a strict-transfer analysis instead carries the sampled-regime selector into the full-active environment. To assess the effect of the evaluation protocol without confounding trained model identities, a separate paired comparison fixes a single Room-SASRec/Streamer-SASRec checkpoint pair, a sampled-development-selected fusion coefficient, and the Memory rule. For each common test event, raw scores over the full-active candidates are computed once and restricted to the sampled subset. Branch scores are standardized separately within each candidate set. This paired design therefore varies candidate membership \emph{together with} the associated normalization reference, while keeping checkpoints, target, and eligible history constant. For event $i$, the contrast is
\begin{equation}
D_i =
\big[u_{10}(M,x_i^{\mathrm{full}})-u_{10}(B,x_i^{\mathrm{full}})\big]
-
\big[u_{10}(M,x_i^{\mathrm{sampled}})-u_{10}(B,x_i^{\mathrm{sampled}})\big].
\label{eq:paired-regime-shift}
\end{equation}
The paired KuaiLive contrast reuses previously examined TEST events and is therefore analyzed as an evaluation-protocol diagnostic. Crossed candidate membership $C\in\{S,F\}$ and branch-standardization reference $R\in\{S,F\}$ distinguish the two sources of the observed ranking-score change. With $g_i(C,R)$ the event-level Memory-minus-Base utility under each configuration, the order-averaged allocations are
\begin{align}
A_{C,i}&=\tfrac12\big[g_i(F,S)-g_i(S,S)+g_i(F,F)-g_i(S,F)\big],\nonumber\\
A_{R,i}&=\tfrac12\big[g_i(S,F)-g_i(S,S)+g_i(F,F)-g_i(F,S)\big].
\label{eq:factorial-allocations}
\end{align}
By construction, $A_{C,i}+A_{R,i}=g_i(F,F)-g_i(S,S)=D_i$. These are descriptive allocations for fixed raw scores: changing candidate membership jointly changes candidate count, composition and ranking competition. Three independently trained checkpoint pairs examine initialization sensitivity on the same users; the additional negative-draw sensitivity is indexed separately in Supplementary S5 and S8. Context-length and history-eligibility analyses assess the robustness of observed conditional patterns.

\subsection{Evaluation Metrics and Statistical Analysis}
\label{sec:exp-statistics}

The principal metric is NDCG@10, computed from the single-positive event utility in Eq.~\eqref{eq:event-ndcg}; hit rate at 10 (HR@10) is secondary. We report mean ranking utility and paired differences for Memory versus Base, Utility versus Base, and Utility versus the equal-count Difficulty control. Specialist invocation rate is the proportion of events assigned to Memory. Evidence-state analyses use the retrospective partition of Eq.~\eqref{eq:diagnostic-states} and distinguish differences in state prevalence from differences in conditional utility.

Mean differences are estimated on paired users, with percentile-bootstrap intervals resampling users (or user clusters for global-time panels with repeated users). Twitch's primary frozen TEST effects use 5,000 paired resamples; matched KuaiLive P0/P2 analyses use 3,000. Inference is conditional on trained models and fixed ranking choices. Model-initialization differences, negative-candidate draws and within-cohort bootstrap uncertainty are reported as distinct variation sources (Supplementary S2, S5 and S8).

\subsection{Implementation Details}
\label{sec:exp-implementation}

KuaiLive Dual-ID uses ReChorus SASRec encoders (64-dimensional embeddings; one attention layer, four heads; maximum history 50). Twitch LiveRec uses history length 16 with context and repeat modules. The 14-feature Utility estimator is histogram gradient boosting (at most 200 iterations, learning rate $0.05$, depth $3$, minimum leaf size $50$, $\ell_2$ penalty $1$, seed $20260918$). Source versions, checkpoint provenance, tuned variants and CPU measurement assumptions are documented in Supplementary S2, S3 and S9.

\section{Experimental Results}
\label{sec:results}

The results follow the decision problem developed above. We first establish how the value of fixed relationship Memory varies relative to Base (Section~\ref{sec:results-heterogeneity}), then test whether its conditional benefit supports better pre-outcome ranking choices (Section~\ref{sec:results-decision}). We next examine how the same value comparison changes across candidate environments (Section~\ref{sec:results-regimes}), before assessing alternative explanations and computational costs.

\subsection{Heterogeneous Utility of Relationship Memory}
\label{sec:results-heterogeneity}

Relationship Memory exhibits substantial event-level heterogeneity relative to the LiveRec Base. Across 44,221 events in the frozen Twitch test evaluation, Memory obtains NDCG@10 of $0.53980$, compared with $0.58211$ for Base, yielding a paired mean difference of $-0.04232$ (95\% CI $[-0.04521,-0.03950]$). We next stratify this contrast by the three target-relative relationship-evidence states defined in Section~\ref{sec:framework-states}, using the same eligible candidates and models within each event.

Figure~\ref{fig:results-evidence-states} compares the state-specific Memory-minus-Base differences on development and test data. The sign is consistent across the two chronological evaluation windows: positive for \emph{recoverable-but-unrepresented} targets and negative for \emph{represented} and \emph{unavailable} targets. On the frozen test set, the recoverable group has a mean gain of $+0.22045$ NDCG@10 over 5,539 events. In contrast, the represented and unavailable groups have mean differences of $-0.01935$ and $-0.18215$, respectively (Table~\ref{tab:results-evidence-states}). The table also reports the Base and Memory scores underlying these contrasts, together with user-paired bootstrap intervals. Thus, the aggregate inferiority of Memory coexists with a substantial positive conditional contrast for targets present in eligible history but absent from the Base's length-limited input.

Target-relative evidence states are assigned retrospectively after the creator is observed. Their practical significance is that a specialist can add substantial ranking value for a subset of requests despite losing in aggregate. Section~\ref{sec:results-decision} tests whether observable, pre-outcome context can identify requests with this favorable relative utility.

\subsection{Decision Value of Predicting Relative Utility}
\label{sec:results-decision}

The recoverable-history advantage in Section~\ref{sec:results-heterogeneity} raises the decision question: can pre-outcome history and Base-score features identify requests on which the specialist is beneficial? The Utility regressor was fitted on Twitch development data, and its invocation threshold was selected using development out-of-fold predictions (Section~\ref{sec:exp-freeze}). Both were frozen before the one-shot evaluation of 44,221 test events. The resulting pointwise policy invoked Memory for 6,650 events (15.04\%).

Table~\ref{tab:results-twitch-policy} reports the resulting rankings. Although always using Memory underperforms Base, the frozen Utility policy attains NDCG@10 of $0.58983$, compared with $0.58211$ for Base. Its paired mean gain is $+0.00772$ (95\% CI $[+0.00641,+0.00903]$); the secondary HR@10 gain is $+0.00945$ (95\% CI $[+0.00776,+0.01117]$). The intervals use 5,000 user-paired bootstrap resamples of the observed event-level differences, with the trained predictors, threshold, and realized selections held fixed. They do not quantify variability from retraining or policy selection.

To test whether the decision gain comes from predicting incremental specialist value rather than Base weakness, we compare Utility with a development-trained Base-Difficulty regressor using the same pre-outcome feature family (Section~\ref{sec:framework-controls}). Difficulty reaches $0.58340$ NDCG@10 when selecting the $6{,}650$ highest-scored test events, giving Utility a paired advantage of $+0.00644$ (95\% CI $[+0.00528,+0.00762]$); the corresponding HR@10 difference is $+0.01196$ (95\% CI $[+0.01033,+0.01364]$). Crucially, $6{,}650$ is the \emph{realized} invocation count of the frozen Utility rule: the Difficulty comparator is ranked retrospectively over the full test batch, not operated with an independently development-frozen invocation threshold. The matched-count contrast isolates the quality of selected events; Difficulty's batchwise top-$m$ score ranking is retrospective, unlike Utility's DEV-frozen pointwise threshold.

The observed selections make this difference concrete. On the 6,650 TEST events selected by the frozen Utility policy, realized Memory-minus-Base NDCG@10 averages $+0.05136$, versus $-0.05890$ over the 37,571 unselected events. The retrospectively equal-count Difficulty subset has mean relative utility of only $+0.00855$. These conditional means follow from the original full-cohort Base, Memory, and policy aggregates at the fixed call count; they describe the value of the realized choices, not new training outcomes or target-dependent policy inputs.

Development out-of-fold selection profiles help explain the difference: Utility enriches recoverable-history events more than Difficulty ($2.72$ versus $1.67$ times prevalence), whereas Difficulty favors unavailable histories ($1.91$ versus $1.03$). These states are assigned retrospectively from the observed target; the selector itself uses pre-outcome descriptors.

The hindsight Oracle selects the $6{,}650$ events with the greatest \emph{realized} Memory-minus-Base utility, reaching $0.64806$ NDCG@10. It bounds only fixed-count choices between these two rankings on the evaluated test events; it is neither deployable nor a general bound for other experts or budgets. Utility captures approximately 11.7\% of its $+0.06595$ gain over Base, while predicted and realized utility correlate weakly (Spearman $0.173$). These gaps limit claims of precise event-level valuation or optimal routing.

\subsection{Candidate-Regime Dependence of Relative Utility}
\label{sec:results-regimes}

The value of selecting Memory also depends on which alternatives must be ranked. We test this dependence in a paired KuaiLive comparison of sampled-active and full-active candidate environments. For 10,222 matched user--time--target events, the sampled-active set ($S$; 575 rooms including the target) is nested in the full-active set ($F$). The checkpoint pair (seed 20260918), sampled-development-selected fusion weight ($\alpha_{\mathrm{room}}=0.125$), Memory rule, eligible histories, and raw model scores remain fixed. Between the native sampled and full-active protocols, Memory-minus-Base NDCG@10 changes from $-0.04120$ (Base $0.60709$, Memory $0.56589$) to $+0.04631$ (Base $0.38571$, Memory $0.43202$). The within-user shift is $+0.08751$ (95\% paired user-bootstrap CI $[+0.08210,+0.09326]$; 3,000 resamples). Both absolute NDCG values decline with the larger ranked set; it is their \emph{relative ordering} that reverses.

The native protocols change both the ranked candidates ($C$) and the reference population ($R$) supplying branch-specific z-score moments. Table~\ref{tab:results-factorial} crosses these two scoring factors using the same raw predictions; off-diagonal cells are analytical configurations rather than additional operational policies. By the two-order allocation of Eq.~\eqref{eq:factorial-allocations}, the mean contribution assigned to ranked-candidate membership is $+0.08827$ (95\% CI $[+0.08287,+0.09397]$), versus $-0.00076$ (95\% CI $[-0.00117,-0.00036]$) for the normalization reference. Their algebraic sum equals the $+0.08751$ native-protocol contrast.

The established sampled-metric literature shows that subsampled ranking comparisons can reverse model orderings \cite{krichene2020sampled}. Our additional evidence identifies how this manifests in a \emph{fixed relationship-Memory-versus-Base decision}: matched events and checkpoints permit a two-order decomposition of ranked candidate membership and branch-score standardization. The membership allocation encompasses candidate count, composition, and competition; the decomposition is descriptive rather than causal.

The directional reversal recurs for checkpoint seeds 20260918, 20260919, and 20260920, with paired native-protocol shifts of $+0.08751$, $+0.08363$, and $+0.08408$, respectively. All three yield negative sampled-active and positive full-active Memory-minus-Base utility. The unweighted mean is $+0.08508$ with a between-checkpoint-pair sample SD of $0.00212$. These are three training realizations evaluated on the \emph{same users}, not independent data replications or a basis for a population-level seed-confidence interval. Within-seed user-bootstrap intervals and across-seed SD characterize different sources of variation; the small negative normalization allocation is not uniformly distinguishable from zero across seeds.

A fixed-checkpoint candidate-draw sensitivity analysis (Supplementary Table~S5.2) evaluated the same 10,222 events at three sampled candidate sizes (128, 256, and 575; three prespecified negative draws each), leaving the seed-20260918 models and full-active reference unchanged. All nine sampled Memory-minus-Base means remained negative (across-draw means $-0.07983$, $-0.06799$, and $-0.04158$ by increasing size), compared with $+0.04631$ under full-active ranking (Supplementary~S5). This post-hoc check supports directional stability only across these draws; it neither isolates candidate-count effects nor constitutes independent held-out TEST evidence.

The paired regimes retain identical target-relative state counts: 4,589 represented, 206 recoverable, and 5,427 unavailable users. Their prevalence-weighted across-seed contributions to the shift are $+0.03869$, $-0.00222$, and $+0.04860$, respectively. The reversal thus arises principally among represented and unavailable targets, rather than from a change in recoverable-history prevalence. These retrospective KuaiLive diagnostics characterize the previously studied cohort, distinct from frozen Twitch selector validation.

\subsection{Robustness and Alternative Explanations}
\label{sec:results-robustness}

We next test which observations underlie the conditional ranking advantage: the available feature families, the composition of Memory, and the Base's history capacity. Twitch DEV supplies these controlled diagnostic comparisons, while a separate KuaiLive reference panel assesses the designated Base's competitiveness (Supplementary S3).

Table~\ref{tab:results-feature-ablation} compares five-fold OOF predictions for 46,878 Twitch DEV events at exactly 6,563 Memory calls, the operating count originally selected by the combined-feature model on DEV. History-only (6 predictors), Base-score-only (8), and combined (14) features yield Utility-minus-Base NDCG@10 gains of $+0.00372$, $+0.00160$, and $+0.00838$, respectively; corresponding predicted-versus-realized Utility Spearman correlations are $0.14791$, $0.09109$, and $0.18990$. The combined family is strongest at this count, but restricted families have different DEV-selected call rates. A replay of the same OOF scores at five further common batch-level budgets (5--30\%; Supplementary Table~S7.1) also favors the combined family at each inspected count (gains $+0.00598$ to $+0.00832$), whereas Base-score-only becomes negative at 30\% ($-0.00282$); gains are not monotonic in calls. These exploratory exact-count analyses do not establish all-budget superiority, causal feature synergy, or a deployable online budget. Their unadjusted bootstrap intervals condition on fitted OOF predictions and selected counts, excluding refitting, operating-point selection and multiplicity uncertainty.

Seven local Memory-parameter configurations on Twitch DEV, including the fixed reference, vary long-term weight, short-window length or decay without retraining Base. The represented-negative, recoverable-positive and unavailable-negative signs persist across these local perturbations; recoverable utility ranges from $+0.13852$ at long-weight 0.30 to $+0.28231$ at 0.60. This restricted result does not extend to the component-removal variants examined next or to arbitrary experts and selectors.

The component-level DEV comparison (Supplementary Tables~S4.1--S4.2) contrasts Short, Long, Popularity and their combinations under a common Base and candidate environment. For 5,879 retrospectively recoverable targets, Long-only achieves NDCG@10 of $0.63890$, versus $0.53298$ for frozen Full Memory and $0.30201$ for Base. The within-user Long-minus-Full contrast is $+0.10592$ (95\% paired-bootstrap CI $[+0.10096,+0.11061]$); Short+Long obtains $0.58673$. The frozen Full Memory mixture remains the prespecified specialist against which conditional value is defined. Long-only also trails Full Memory on unavailable targets (by $0.03208$ NDCG@10 on DEV), and both variants remain below Base overall (Long-only $0.52761$, Full $0.52170$, Base $0.57185$). The component contrasts therefore reveal a trade-off across histories rather than an empirically selected replacement for the fixed expert.

With canonical Memory rankings held fixed, separately trained Twitch DEV Base models using context lengths $L=8,16,32$ achieve NDCG@10 of $0.52619$, $0.57185$, and $0.59663$; Memory remains at $0.52170$ (Supplementary Table~S6.1). On matched events changing retrospectively from recoverable to represented, Memory-minus-Base utility declines by $0.44748$ ($L=8\rightarrow16$, $n=5{,}055$) and $0.43229$ ($L=16\rightarrow32$, $n=3{,}617$). These differences equal the negative Base gains for fixed Memory, but independently retrained Base weights prevent isolation of a pure history-visibility effect; groups require the observed target.

Recency is also nonmonotonic on DEV: Memory-minus-Base utility is $+0.04606$ for target-creator recurrence after 1--4 events, $-0.15268$ after 9--16, and $+0.25668$ after 17--32. These target-defined bins describe association with historical recurrence, with user activity and candidate difficulty varying across groups (Supplementary Table~S6.4).

Together, the DEV diagnostics locate Memory's strongest gains in particular history conditions while the fixed-Base comparisons establish their dependence on model capacity. Auxiliary Baselines were evaluated under limited, nonuniform tuning budgets, and their KuaiLive checkpoint differs from Section~\ref{sec:results-regimes} (Supplementary Tables~S3.1--S3.3); they serve to contextualize the designated Base rather than rank comprehensively tuned alternatives.

\subsection{Computational Considerations}
\label{sec:results-efficiency}

On frozen Twitch TEST, Utility invoked Memory for 6,650 of 44,221 events (15.04\%; Section~\ref{sec:results-decision}). Mandatory Base and feature computation makes this a specialist-use rate, not a latency saving.

A separate KuaiLive CPU benchmark (575 candidates) measured Base mean latency $0.991$\,ms (pooled P95 $1.276$\,ms), versus $2.007$\,ms (P95 $2.905$\,ms) for Selective HGB at 14.25\% Memory calls. Selection thus added $1.016$\,ms ($2.03$ times Base). Three hosted CPUs each timed 1,200 warmed single-threaded queries with cached histories and prepared feeds. Gate inference was timed but routing followed archived masks; these measurements describe scoring overhead, not deployed routing.

The timed path includes Base scoring, 14 features, gate inference and conditional Memory ranking. The benchmarked KuaiLive HGB uses $T=81$ trees of maximum depth $D=3$, yielding $O(TD)$ traversal after feature construction; candidate Memory scoring requires $O(C)$ time given cached relationship state. Feature construction, cache maintenance and I/O incur additional costs. Supplementary Table~S9.1 reports unmatched gate costs and resource footprints; these measurements establish neither equal-utility acceleration nor online deployment performance.
